# Plan — Construct Mobile (Flutter, AI-First)

## Classification

**Type:** Native mobile application (iOS + Android)
**Framework:** Flutter (Dart)
**Architecture:** AI-first conversational interface with push notifications and Pulses integration
**Auth:** Same as desktop — existing Construct auth flow (OAuth session, token refresh)
**Design:** Match desktop Construct theme (dark/light, accent colors, typography scale adapted for mobile density)

---

## Identity

- **App Name:** Construct
- **Bundle ID:** `space.construct.mobile`
- **Min Targets:** iOS 16+, Android API 28+ (Android 9)

---

## Core Concept

The mobile app is **not** a shrunken desktop — it's an AI-first command center. The primary interface is a conversation with Construct. Users speak or type requests, and the assistant routes them to the appropriate Space actions behind the scenes. Results render as rich cards inline in the chat. Push notifications and Pulses deliver proactive intelligence without opening the app.

---

## Screens / Pages

**6 screens total:**

| # | Route | Purpose |
|---|-------|---------|
| 1 | `/` | **Chat** — Full-bleed conversation view. Text + voice input. Rich cards for Space results (email previews, calendar events, task cards, etc.). This is the home screen. |
| 2 | `/thread/:id` | **Thread Detail** — Deep-dive into a specific result card (full email thread, event details, issue view). Swipe-back to chat. |
| 3 | `/pulses` | **Pulses Feed** — Chronological list of Pulse summaries. Tap to expand. Badge count on tab. |
| 4 | `/notifications` | **Notifications** — System + Space notifications. Grouped by source. Tap to act (reply, approve, snooze). |
| 5 | `/spaces` | **Spaces Directory** — Grid of installed Spaces with status indicators. Tap opens a Space-specific quick-action sheet (not full Space UI). |
| 6 | `/settings` | **Settings** — Account, notifications preferences, Pulse schedules, theme toggle, voice input config, connected accounts. |

**Navigation:** Bottom tab bar with 4 tabs — Chat (home), Pulses, Notifications, Settings. Spaces accessed via a floating pill / drawer from Chat.

## Architecture

### State Management

- **Riverpod** for app-wide state (auth, user profile, theme, notification badges)
- **Conversation state** managed as a stream of message objects (user messages, assistant responses, rich cards, loading indicators)
- **Local cache** via Hive or Isar for offline access to recent conversations and Pulse summaries
- **No local Graph** — all data lives on the Construct backend; the mobile app is a thin client that calls the same APIs the desktop app uses

### API Layer

- **HTTP client:** Dio with interceptors for auth token injection and refresh
- **Streaming:** SSE (Server-Sent Events) for real-time assistant responses (same streaming protocol as desktop)
- **WebSocket:** For live notification delivery when app is foregrounded

### Auth Flow

- Same session/token mechanism as desktop Construct
- On first launch: open an in-app browser (ASWebAuthenticationSession on iOS / Custom Tabs on Android) to the Construct login page
- Receive auth token via deep link callback (`construct://auth/callback`)
- Store tokens in platform secure storage (Keychain / EncryptedSharedPreferences)
- Biometric unlock option for subsequent launches (FaceID / fingerprint)

## Push Notifications

### Infrastructure

- **Firebase Cloud Messaging (FCM)** for Android
- **APNs** for iOS
- **Backend integration:** Construct backend registers device tokens on login, sends push payloads when:
  - A Pulse fires and produces a non-quiet summary
  - A Space emits a notification (new email, calendar reminder, task assignment, etc.)
  - The assistant has a proactive message (scheduled reminder, completed background task)

### Notification Types

| Type | Payload | Tap Action |
|------|---------|------------|
| `pulse_summary` | Title, 2-line preview, pulse_id | Open `/pulses` scrolled to that summary |
| `mail_new` | From, subject, thread_id | Open `/thread/mail:{thread_id}` |
| `calendar_reminder` | Event title, time, event_id | Open `/thread/calendar:{event_id}` |
| `task_assigned` | Issue identifier, title, issue_id | Open `/thread/pm:{issue_id}` |
| `chat_message` | Sender, preview, channel_id | Open `/thread/chat:{channel_id}` |
| `generic_space` | Space name, message, action_uri | Open the action URI in chat context |

### Notification Settings (per-type toggles)

- Global: on/off, quiet hours (schedule)
- Per Space: on/off
- Per Pulse: on/off (inherits from Pulse config)
- Delivery: sound, vibration, badge count

## Pulses Integration

### Mobile-Specific Behavior

- Pulses run on the backend (same scheduler as desktop) — the mobile app is a **consumer**, not a runner
- `/pulses` screen shows a reverse-chronological feed of Pulse outputs
- Each Pulse card shows: title, timestamp, summary (rendered markdown), source badges (which Spaces contributed)
- Tap to expand shows the full summary with action buttons (reply to email, open event, etc.)
- Pull-to-refresh triggers a check for new Pulse results
- Badge count on the Pulses tab for unread summaries

### Creating/Editing Pulses from Mobile

- Users can say "set up a morning briefing" in chat → assistant uses the same Pulse propose/confirm/create flow
- `/settings` → Pulses section shows all active Pulses with enable/disable toggles
- Full Pulse editing (schedule, recipe, delivery) happens through the chat assistant, not a form UI

## Conversation / Chat Engine

### Message Types

```
UserTextMessage     — plain text input
UserVoiceMessage    — transcribed voice input (STT via platform APIs)
AssistantText       — markdown-rendered response
AssistantCard       — rich card (email preview, event, issue, Pulse summary)
AssistantAction     — confirmation prompt (send email? create event? approve?)
SystemMessage       — connection status, errors, welcome
LoadingIndicator    — streaming dots while assistant responds
```

### Voice Input

- Platform-native speech-to-text (SFSpeechRecognizer on iOS / SpeechRecognizer on Android)
- Hold-to-talk button next to text input
- Transcription streams into the text field in real-time; user confirms or edits before sending
- No voice output in v1 (text responses only) — voice output is a v2 candidate

### Rich Cards

Cards render inline in the chat and are tappable to open `/thread/:id`. Card types:

- **EmailCard** — from, subject, snippet, timestamp, unread indicator
- **EventCard** — title, time range, location, attendee avatars
- **IssueCard** — identifier, title, status badge, priority, assignee
- **PulseSummaryCard** — title, bullet summary, source badges
- **NoteCard** — title, preview, page icon
- **ActionCard** — confirmation prompt with Accept / Reject buttons
- **ListCard** — generic list of items (search results, contacts, etc.)

## Data Model (Local)

Minimal local persistence — the app is online-first.

### Hive Boxes (or Isar Collections)

| Box | Fields | Purpose |
|-----|--------|---------|
| `auth` | access_token, refresh_token, expires_at, user_id, org_id | Secure storage |
| `conversations` | id, messages[], created_at, updated_at | Cache recent conversations (last 50) |
| `pulse_results` | id, pulse_id, title, summary, sources[], created_at, is_read | Offline Pulse feed |

| `preferences` | theme, quiet_hours, per_space_notification_settings | Local settings |
| `device` | fcm_token, apns_token, device_id, registered_at | Push registration |

## User Flows

### 1. First Launch

1. Splash screen → "Sign in to Construct" button
2. Opens in-app browser to Construct auth page
3. User logs in (same credentials as desktop)
4. Redirect to `construct://auth/callback?token=...`
5. App stores token, registers device for push notifications
6. Lands on Chat screen with welcome message: "Welcome to Construct Mobile. What can I help with?"

### 2. Morning Briefing (Pulse)

1. Push notification at 9:00 AM: "☀️ Morning Briefing ready"
2. User taps → opens `/pulses`, scrolls to today's briefing
3. Sees: 3 unread emails needing response, 2 meetings today, 1 overdue task
4. Taps email card → opens thread detail → taps "Reply" → types response in-thread
5. Back to Pulses → marks briefing as read

### 3. Quick Email Reply

1. User opens Chat, types: "reply to Sarah's last email saying I'll review it tomorrow"
2. Assistant fetches Sarah's latest thread, drafts a reply, shows ActionCard: "Send this reply to Sarah Torres?"
3. User taps "Send" → reply sent → confirmation card appears

### 4. Voice Calendar Check

1. User holds voice button: "What's on my calendar today?"
2. Transcription appears, auto-sends
3. Assistant returns a list of EventCards for today
4. User taps an event → sees full detail with attendees and location

### 5. Notification-Driven Task

1. Push notification: "🎫 ENG-142 assigned to you: Fix OAuth refresh loop"
2. User taps → opens issue detail thread
3. Types: "what's the context on this?" → assistant summarizes the issue + comments
4. Types: "move it to In Progress" → assistant updates status, confirms

## Backend Requirements (not built in this plan — dependencies)

The mobile app assumes these backend capabilities exist or will be built:

1. **Push notification service** — accepts device token registration, dispatches FCM/APNs payloads when events occur
2. **SSE streaming endpoint** — same as desktop uses for real-time assistant responses
3. **Pulse results API** — `GET /pulses/results` returning chronological Pulse outputs
4. **Notification history API** — `GET /notifications` with pagination and mark-read
5. **Auth deep-link support** — callback URI scheme `construct://auth/callback` registered
