What happens between the chat box and the model when brain is the sidecar. Click a step to expand.

Pi-shape note. Brain ships only 8 tool schemas per turn (~5KB): read, write, edit, bash, list_tools, call_tool, list_skills, load_skill. Every other capability (git, grep/glob, lsp, graph, web, space.*, dispatch_subagent, etc.) is registered hidden — the model finds it via list_tools and invokes via call_tool(name, args). Skills follow the same pattern. Operator's per-turn payload was ~91KB.

HTTP

POST /v1/stream → brain

›
Direct webview fetch — no Tauri IPC marshalling for the prompt path

Webview's fetch() opens an SSE stream to brain at 127.0.0.1:60182. No length-prefixed framing, no Rust hop — the JS body is the raw {id, type:"prompt", payload} envelope.

Why this is cheaper than operator

  • Webview → loopback HTTP: 1 hop. Operator went webview → Rust IPC → TCP framing → operator: 3 hops.
  • Same stream serves tool callbacks (see SSE back-channel below); no second connection.
  • CORS allows http://localhost:60200 (Vite dev) so the same client works without Tauri.

Brain dispatch — sidecar.Server

›
Routes prompt (or stream alias) → runPrompt → handlePrompt

HTTP server reads the wire envelope, looks up the handler keyed by type, and calls it with an emit callback that flushes each chunk as an SSE data: line.

Stream aliases (operator-compat)

  • ai.chat_stream, experimental.run.small_stream, architect_stream, vibe_stream, agents.dispatch_stream — all adapter shims that translate to the canonical {prompt, model, ...} shape and call runPrompt.
  • cancel wire op fires the per-request context.CancelFunc tracked in cancelTracker.

GO

handlePrompt — assemble request

›
Picks provider, builds system prompt, binds session, persists user turn

Single function. No "runner" / "context" / "morpheus" indirections — the whole request setup is linear.

In order

  • Provider routing. If payload had no provider, inferProviderFromModel walks the catalog snapshot for a slug owning that model id; falls back to family prefix (claude-*, gpt-*, gemini-*).
  • Model default. If no model, ask the catalog for the provider's default; else defaultModel.
  • System prompt. Explicit pl.System wins; else agent.SystemPrompt by agent_id; else defaultSystemPrompt. skill.BuildSystemPrompt appends a "N skills loaded — call list_skills" pointer (no per-skill catalog inline).
  • Provider build. buildProvider resolves credentials: enforced org key → provider_key:<slug> in settings → env vars → non-enforced org key. Bespoke clients for Anthropic / Google / OpenAI-Codex; everyone else is the OpenAI-compat client with catalog BaseURL.
  • Caps. Catalog lookup returns model capabilities (caching, structured, tools, vision, reasoning) — passed to the provider so it opts into the right API features.
  • Session. Load history JSONL; assign id if new. Bind taskStore.SetSession(id) so task_create/_update/_list bucket correctly.
  • Frontend SSE channel. bindFrontend installs an emitter so any in-process tool can push a tool_request down the same stream the prompt is streaming back on.
  • Persist user turn before calling the model so an abort still leaves a complete log.

LOOP

agent.Agent.Run — turn loop

›
Compact → stream → execute tools → loop until end_turn or max iterations

The single agent loop. Decorated with hooks, an LLM-summarised compactor, and a permission gate; the body itself is ~80 lines.

Each iteration

  • CompactIfNeeded — if char count over 0.85 × MaxChars, summarise elided middle via a cheap model from buildSummarizer. EmergencyCompact strips tool_result bodies as a last resort.
  • Provider Stream with the visible tool schemas (just 8 of them).
  • For each tool_use block: run hooks (pre), permission gate (deny/ask/allow), execute the tool, truncate result to ≤15K (10K head + 4K tail), run hooks (post).
  • Append assistant message + tool_result message to history.
  • Stop when stop_reason ≠ "tool_use".

API

Provider.Stream — SSE to upstream

›
Translates the agent's request shape to the upstream's wire format

Five provider implementations, all behind the same Stream(ctx, req, emit) error interface. Each one translates SSE events into brain's provider.Event shape so the agent loop is provider-agnostic.

Implementations

  • Anthropic — Messages API + OAuth (Claude Pro/Max). Prompt cache split: static prefix gets cache_control: ephemeral, dynamic suffix does not. Adds the Claude Code identifier as a leading system block for OAuth traffic.
  • Google — Gemini streamGenerateContent. Sanitizes input schemas (drops $schema, additionalProperties) so functionDeclarations accept brain's tool shapes.
  • OpenAI — chat-completions. Used for plain OpenAI + DeepSeek / Xiaomi / OpenRouter / Kimi / xAI / Alibaba / any catalog provider with a BaseURL.
  • OpenAICodex — ChatGPT Plus/Pro via chatgpt.com/backend-api/codex/responses. Responses API event types translated to brain's Event types.
brain/provider/anthropic.go — Messages API + OAuth headers + cache split brain/provider/google.go — Gemini SSE + schema sanitization brain/provider/openai.go — chat-completions (OpenAI-compat backend for many slugs) brain/provider/openai_codex.go — Codex Responses API brain/provider/orgkeys.go — org-supplied API keys from source gateway

EXEC

Tool execution — 3 paths

›
Native Go / call_tool dispatch / SSE back-channel — picked by tool kind

Every tool call lands in tool.Registry.Execute; what happens next depends on the tool.

Path A — Native, in-process

  • read, write, edit, bash — direct syscalls.
  • Hidden tools via call_tool(name, args) — registry lookup, execute. The model uses these after discovering them via list_tools.

Path B — SSE back-channel to frontend

  • space_list_actions, space_run_action, ask_user, start_preview, request_project_setup, permission.request.
  • Brain emits a tool_request chunk on the active prompt's SSE stream. The frontend's bridgeListener dispatches against live Pinia/DOM state and POSTs the result to /v1/tool_response. Brain's bridge.Frontend.Resolve unblocks the waiting call.
  • 2 hops (brain ↔ frontend). No Tauri shell in the loop.

Path C — HTTP bridge fallback (native OS ops)

  • space.screenshot, browser.*, construct.mouse_*.
  • Routes to the legacy desktop bridge listener on :60101 (operator's old shape). HTTP POST with bearer token. Webview can't reach screenshots / native automation, so this path stays.

SSE

Stream chunks → webview

›
Same SSE response — carries text deltas, tool calls, tool results, and bridge requests

The provider stream pushes text_delta / tool_use_start / tool_use_input_delta / block_stop events into brain's emit fn. Brain forwards them as wire.Response chunks on the active SSE stream, mixed with:

  • session — issued once at start with the resolved session_id
  • tool_call / tool_result — for the UI's tool-card rendering
  • tool_request — brain asking the frontend to run a bridge method (Path B above)
  • usage — token accounting per round
  • end — final stop with stop_reason

Frontend rendering

  • useBrain().stream() reads data: lines and dispatches each chunk to onChunk/onDone/onError handlers.
  • AssistantModal appends text deltas to the live bubble, surfaces tool calls as bracketed lines, scrolls.

Session persisted

›
JSONL per session — assistant turn + tool_result turn appended each round

OnMessages callback fires after each provider round; brain appends the assistant message and (optional) tool-result message to <sessions-dir>/<session_id>.jsonl. Telemetry sink records token usage per turn.
