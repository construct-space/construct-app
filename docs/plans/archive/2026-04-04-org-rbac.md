# Organization RBAC System

## Problem

Every org page currently shows all controls to all members. A regular member can edit the owner, delete members, disable the org, change settings, and send invites. There's no permission enforcement — neither in the frontend (UI visibility) nor comprehensively in the backend (API authorization).

## Roles

Four roles, strictly hierarchical:

| Role | Who | Can do |
|------|-----|--------|
| **owner** | Created the org. Exactly one. | Everything. Transfer ownership. Delete org. |
| **admin** | Appointed by owner. | Manage members, departments, teams, invites, settings, provider keys. Cannot delete org or remove owner. |
| **manager** | Appointed by admin/owner. | Manage own department's members and teams. Read-only for other departments. Cannot change roles, settings, or provider keys. |
| **member** | Default for new joins. | Read-only. Can view members, departments, teams. Can edit own profile (name, title, bio). Cannot manage anything. |

## Implementation Plan

### Phase 1: Frontend — Role-Aware UI

**Goal:** Hide controls that the current user's role doesn't allow. This is UX enforcement — the backend is the real gate.

#### 1.1 Add `useOrgPermissions` composable

Create `frontend/spaces/org/composables/useOrgPermissions.ts`:

```typescript
// Returns role-based permission checks for the current user
export function useOrgPermissions() {
  const authStore = useAuthStore()
  const { members } = useOrgData()

  const currentMember = computed(() => {
    const userId = authStore.user?.id
    if (!userId) return null
    return members.value.find(m => m.user_id === userId) ?? null
  })

  const role = computed(() => currentMember.value?.role ?? null)
  const isOwner = computed(() => role.value === 'owner')
  const isAdmin = computed(() => role.value === 'owner' || role.value === 'admin')
  const isManager = computed(() => isAdmin.value || role.value === 'manager')

  // Member permissions
  const canAddMember = isAdmin
  const canEditMember = (memberId: string) => {
    if (isAdmin.value) return true
    return currentMember.value?.id === memberId // can edit self
  }
  const canRemoveMember = (memberRole: string) => {
    if (!isAdmin.value) return false
    if (memberRole === 'owner') return false // nobody removes owner
    return true
  }
  const canChangeRole = isAdmin
  
  // Department/team permissions
  const canManageDepartments = isAdmin
  const canManageTeams = isAdmin // TODO: manager for own dept
  
  // Invites
  const canManageInvites = isAdmin
  
  // Settings
  const canEditSettings = isAdmin
  const canDisableOrg = isOwner
  const canManageProviderKeys = isAdmin
  
  // Activity
  const canViewActivity = isManager

  return {
    currentMember, role, isOwner, isAdmin, isManager,
    canAddMember, canEditMember, canRemoveMember, canChangeRole,
    canManageDepartments, canManageTeams,
    canManageInvites,
    canEditSettings, canDisableOrg, canManageProviderKeys,
    canViewActivity,
  }
}
```

#### 1.2 Update all org pages to use permissions

**Pages to update:**
- `OrgMembers.vue` — hide "Add Member" button for non-admin. Hide row click for members who can't edit.
- `members/[id].vue` — hide Edit button, danger zone based on `canEditMember(id)` and `canRemoveMember(role)`. Members can only edit their own profile.
- `OrgDepartments.vue` — hide "Add Department" for non-admin.
- `departments/[id].vue` — hide edit/delete for non-admin. Managers can edit own dept only.
- `teams/[id].vue` — hide edit/delete for non-admin.
- `OrgInvitations.vue` — hide entirely for non-admin (or show read-only list).
- `OrgActivity.vue` — hide for members (show for manager+).
- `OrgSettings.vue` — already fixed (owner-only danger zone, admin-only edit).
- `OrgDashboard.vue` — hide quick action buttons for non-admin.

#### 1.3 Hide sidebar nav items by role

Members shouldn't see Invitations, Activity, or Settings nav items. Update `manifest.json` or the sidebar rendering to filter by role.

### Phase 2: Backend — API Authorization

**Goal:** Enforce permissions at the API level. The frontend hides controls, the backend rejects unauthorized requests.

#### 2.1 Add role check helpers to org handler

```go
// requireAdmin returns the caller and checks admin+ role. Returns nil + 403 on failure.
func requireAdmin(w http.ResponseWriter, r *http.Request) *models.OrgMember {
    caller := getMember(UserID(r))
    if caller == nil {
        WriteJSON(w, 404, map[string]string{"error": "not in an organization"})
        return nil
    }
    if caller.Role != "owner" && caller.Role != "admin" {
        WriteJSON(w, 403, map[string]string{"error": "admin access required"})
        return nil
    }
    return caller
}

// requireOwner checks owner role.
func requireOwner(w http.ResponseWriter, r *http.Request) *models.OrgMember {
    caller := getMember(UserID(r))
    if caller == nil {
        WriteJSON(w, 404, map[string]string{"error": "not in an organization"})
        return nil
    }
    if caller.Role != "owner" {
        WriteJSON(w, 403, map[string]string{"error": "owner access required"})
        return nil
    }
    return caller
}
```

**Key fixes needed:**

2. `DeleteMember` — must reject if target is owner
3. `UpdateMember` — allow self-edit for non-admins (limited fields)

### Phase 3: Manager Scope (future)

Managers can manage their own department only. This requires:
- Checking `caller.department_id === target.department_id` for member operations
- Checking `caller.department_id === department.id` for department/team operations
- This is more complex and can be added incrementally
