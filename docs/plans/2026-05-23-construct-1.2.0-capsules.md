# Construct 1.2.0 — Capsules

**Status:** Architecture proposed, implementation not started.
**Codename:** Capsules.
**Pairs with:** `2026-05-20-automations.md` (scheduler), `2026-05-17-cross-space-agent-dispatch.md` (navigate_space), `2026-05-04-space-binary-sandbox.md` (sandbox primitives).
**Informed by:** Hermes Agent (NousResearch) and agentskills.io — what we keep, what we adapt, what we explicitly reject.

This document is the 1.2.0 release plan. The headline is **skills carry
tools**: every skill is a capability capsule that ships its own tools,
references, and scripts. Loading a skill mounts its tools for the
duration of the subtask; unloading unmounts them. The agent's always-on
tool surface stays small (the pi-shape we already enforce); capability
expands contextually.

The secondary axis is **procedural memory**: when the agent succeeds at
a non-trivial task, it materialises the trajectory as a new skill,
including any helper tools it needed. The agent grows its own
capabilities, in writing, on disk, reviewable.

The tertiary axis is **trajectory → training**: completed traces ship
to telemetry as ShareGPT-formatted data, feeding operator-specific
LoRAs (Tank, Apoc, Trinity, Mouse, Oracle, Neo).

---

## Why now

Two pressures meet.

**From the product side**, brain's hidden tool list keeps growing.
`graph_*` (5 tools), `git_*` (5 tools), `space_*`, `org_*`,
`notebook_*`, `pdf_*` — all in `brain/tools.go`, all consuming
discovery cycles via `list_tools` / `call_tool` even when irrelevant.
The old operator at `~/Desktop/operator/` had 30+ globally registered
`builtin_*.go` tools and was demonstrably less efficient: too much
surface, too much per-turn schema, model attention diluted. We
escaped that with the pi-shape (`feedback_brain_pi_shape`), but the
solution was "hide tools behind `call_tool`," not "scope tools to
the work."

**From the agent-improvement side**, Hermes ships a procedural memory
loop (`skill_manage`) that turns successful trajectories into reusable
skills. We have telemetry, Tinker credits, mlx-lm-lora DPO, and a
locked Source operator family — every piece needed to feed runtime
into fine-tuning — but no plumbing to connect them.

Capsules solves both: skills become the unit of capability *and* the
unit of procedural memory. One concept, two payoffs.

## Core principles

1. **Skills are capability capsules.** A skill ships `SKILL.md` +
   optional `tools/`, `references/`, `scripts/`, `assets/`. Loading the
   skill mounts its tools; unloading unmounts them. The always-on tool
   surface stays at the pi-shape minimum.
2. **Tools live with the skill that uses them.** A `graph` skill owns
   `graph_init`, `graph_generate`, `graph_push`, `graph_migrate`,
   `graph_status`. A `git` skill owns `git_*`. Brain ships these as
   reference skills, not hidden builtins.
3. **Procedural memory grows capability, not just prose.** The
   `skill_manage` tool can write new SKILL.md files *and* synthesise
   helper tools the skill exposes. Successful trajectories materialise
   as installable skills.
4. **Three-tier disclosure.** `list_skills` → `skill_view(name)` →
   `skill_view(name, path)`. The model loads the slice it needs, not
   the whole skill body.
5. **Scope hierarchy is space > org > user > builtin.** Skills live at
   one of four scopes; precedence is explicit; collisions are
   resolved by scope, not by load order.
6. **No system-prompt mutation.** Bundles and skill loads inject a
   user-message instruction, not a system-prompt edit. Preserves
   prefix cache; matches how the model was trained.
7. **Runtime feeds training.** Brain writes ShareGPT-formatted traces
   to telemetry-api with consent. Operator-specific datasets feed
   per-operator LoRAs via the existing Tinker / mlx-lm-lora pipelines.
8. **Cron pairs with the existing scheduler.** Server scheduler
   (`api/source/internal/scheduler/`) owns user-visible schedules,
   cross-device durability, push-wake. Brain owns in-process ticks:
   housekeeping, supervision, trajectory flush, server-fire receiver.
   Both share one job-shape so the loop in brain is uniform.

## Skill format

```
~/.construct/profiles/<id>/skills/<scope>/<name>/
├── SKILL.md          # frontmatter + when-to-use + procedure + pitfalls + verification
├── tools/            # optional — capability capsule's own tools
│   ├── pg_query.json     # JSON schema (input + output)
│   ├── pg_query           # handler binary (sidecar JSON-RPC)
│   └── manifest.yaml      # tool list, permission level, env requirements
├── references/       # long-form docs the agent loads on demand (tier 2 disclosure)
├── scripts/          # helper scripts the skill calls internally
└── assets/
```

### SKILL.md frontmatter

```yaml
---
name: backend
description: Postgres + migrations + API scaffolding
version: 0.3.0
scope: any                       # any | builder | spacekit (existing field)
category: data
tags: [postgres, sql, migrations]

# new in 1.2
requires:
  env: [DATABASE_URL]
  binaries: [psql]
  scopes: [org]                  # only available when active scope ≥ org
provides:
  tools:                         # tools mounted when this skill is loaded
    - name: pg_query
      schema: tools/pg_query.json
      handler: tools/pg_query    # sidecar binary
      permission: prompt         # always | prompt | deny
    - name: pg_explain
      schema: tools/pg_explain.json
      handler: tools/pg_explain
      permission: always
---

# Backend skill

## When to use
Use this skill when the user asks about database schemas, migrations, or
needs to query the Construct graph from inside an action.

## Procedure
1. …

## Pitfalls
- Don't run `pg_query` against `graph-1` without an explicit user request — it's the prod DB.

## Verification
- After a migration, run `pg_explain` against the touched tables.
```

### Tool handler — sidecar binary, JSON-RPC over stdin/stdout

Three handler kinds are theoretically possible (inline Go, sidecar
binary, HTTP). We pick **sidecar binary** as the only supported path
for 1.2.0:

- **Polyglot.** Skill authors ship Go / Python / Rust / TS / anything.
- **Same model as Spaces.** `useSpaceTool` already handles
  path-control + caps + signing; we reuse the same sandbox primitives.
- **Distributable.** A skill is a directory; the tool is part of it.
  Install = unpack; uninstall = delete.

Brain spawns the binary on first tool call, keeps it alive for the
session, sends JSON-RPC requests, reads streaming responses. The
binary's path is resolved against the skill's directory; the env is
filtered against the skill's declared `requires.env`; the working
directory is the project root (or the space's scratch dir for
space-scope skills).

Inline Go and HTTP are explicit non-goals for 1.2:
- Inline Go defeats the "skills are distributable" story.
- HTTP requires a running service the user has to start — brittle.

## Brain changes

### Tool registry (`brain/tools.go`)

The always-on visible set drops from 9 to **6**:

```
read, write, edit, bash, list_skills, load_skill
```

Everything else moves behind skills:

| Old hidden tool          | New skill                 |
|--------------------------|---------------------------|
| `graph_init`, `graph_generate`, `graph_push`, `graph_migrate`, `graph_status` | `graph` skill |
| `git_status`, `git_diff`, `git_log`, `git_commit`, `git_branch`               | `git` skill   |
| `space_list_installed`, `space_run_action`, `space_snapshot`, `navigate_space`, `space_lifecycle_*` | `spaces` skill (always-loaded for General agent) |
| `org_invite`, `org_members`, `org_departments`                                | `org` skill   |
| `marketplace_search`, `marketplace_show`                                      | `marketplace` skill |
| `notebook_read`, `notebook_edit`, `pdf_read`                                  | `documents` skill |
| `web_fetch`, `web_search`                                                     | stay always-on (every operator needs them) |
| `check_env`, `glob`, `grep`, `list_dir`                                        | stay hidden (used by every skill, too narrow to capsulise) |
| `ask_user`                                                                    | stays always-on |

After the migration, the visible-or-hidden builtin tool count drops
from ~30 to ~10. The rest are skill-mounted.

### `SkillRegistry` (`brain/tool/load_skill.go`)

Existing struct extended:

```go
type SkillEntry struct {
    ID          string
    Name        string
    Description string
    Path        string
    Body        string
    Tools       []SkillTool         // new
    Scope       string              // user | org | space | builtin
    Requires    SkillRequirements   // env / binaries / scope gates
}

type SkillTool struct {
    Name        string
    Schema      json.RawMessage
    HandlerPath string                   // resolved against skill dir
    Permission  string                   // always | prompt | deny
}
```

`load_skill` becomes a *mount*: registers the skill's tools into the
per-session tool registry, returns the body + tier-1 references summary.
`unload_skill` (new) cleans up; `bash` and `read` remain always-on.

Auto-unload at task boundary: when the agent emits `end_turn` and no
follow-up arrives within N minutes, mounted skills are unloaded so the
next prompt starts clean. Configurable; defaults to "unload at session
end."

### `skill_manage` (new tool — hidden, agent-only)

Actions:

| Action      | Purpose                                       | Notes |
|-------------|-----------------------------------------------|-------|
| `create`    | New SKILL.md from scratch                     | Patch-friendly; full content required. |
| `patch`     | Targeted edit                                 | `old_string` + `new_string`; cheap. |
| `edit`      | Full rewrite                                  | Use sparingly; large diffs. |
| `delete`    | Remove a skill                                | Confirmation step in frontend modal. |
| `write_file`| Add/update a reference or asset file          | `path` relative to skill dir. |
| `remove_file` | Delete a file inside the skill              | |
| `add_tool`  | Synthesise a new tool inside the skill        | Writes `tools/<name>.json` schema + sidecar binary; permission defaults to `prompt`. |

Triggers documented in the system prompt for the agent (not enforced):
1. Task succeeded after ≥ 5 tool calls.
2. Agent recovered from a dead end and the new path worked.
3. User corrected the agent's approach.
4. A non-trivial workflow was discovered.

`add_tool` is the procedural-memory-grows-capability lever. The agent
writes a small Go program (compiled by brain on first use) or a
shell-script wrapper; the schema is generated from observed call
patterns; permission level defaults to `prompt`. Users can review +
edit in the frontend's Skills panel.

### Three-tier disclosure

`load_skill` already returns the body. Extend with:

```
load_skill(name)             # tier 1: returns frontmatter + body
load_skill(name, "refs/x.md") # tier 2: returns a single reference file
```

Cheap change to `brain/tool/load_skill.go`. The model can pull a single
long-form reference without inflating context.

### Bundles (`~/.construct/skill-bundles/<name>.yaml`)

Slash-command shape:

```yaml
name: backend-pr
description: Backend feature — write tests, implement, open PR
skills: [git, backend, code-review]
instruction: |
  Always start by writing failing tests, then implement.
  Open the PR with the project's standard checklist.
```

When the user types `/backend-pr <what>`, frontend sends a fresh user
message with the instruction prepended and the listed skills
pre-loaded. **No system-prompt mutation.** Bundles are saved per-profile
and per-org.

### Trajectory exporter (`brain/telemetry/trajectory.go`)

After each turn, if the user has opted in to trace export (telemetry
setting), brain serialises the turn as ShareGPT:

```json
{
  "trace_id": "01HQ…",
  "operator": "trinity",
  "skills_loaded": ["backend", "git"],
  "messages": [
    {"from": "system", "value": "<system prompt>"},
    {"from": "human", "value": "<user message>"},
    {"from": "assistant", "value": "<reasoning + tool calls in XML envelope>"},
    {"from": "tool", "value": "<tool result>"},
    {"from": "assistant", "value": "<final response>"}
  ],
  "outcome": "succeeded" | "abandoned" | "errored",
  "duration_ms": 12340
}
```

Trajectories are protected at head + tail (per Hermes's
`trajectory_compressor.py` design) — first 3 turns and last N turns
preserved verbatim; middle compressed with an aux LLM summary when the
trace exceeds 16k tokens.

Telemetry-api gains `POST /api/traces` (parallel to
`POST /api/errors`). Server stores compressed; export job rolls
operator-specific JSONL daily for the fine-tune pipelines.

### `brain/cron` — in-process scheduler

Port `internal/cron/cron.go` + `module.go` from old operator.

Job types:

| Job                   | Purpose                                                     |
|-----------------------|-------------------------------------------------------------|
| `HousekeepingJob`     | Skill-cache GC, session DB vacuum, prompt-cache refresh.   |
| `SupervisionJob`      | Watch subagent / swarm worker; kill if hung past timeout.  |
| `TrajectoryFlushJob`  | Batch-send pending traces to telemetry-api when wifi + ≥ 80% battery. |
| `ServerFireJob`       | Receive `scheduler.claim_now` from devicebus; race to claim; if won, materialise the task's `Action` as a brain run. |

Job *shape* matches `api/source` scheduler's `Schedule` JSON so the
brain's loop can ingest both local-only ticks and server-pushed fires
uniformly:

```go
type Job struct {
    ID       string
    Schedule scheduler.Schedule   // interval | daily | weekly | once
    Action   scheduler.Action
    Local    bool                 // true = brain-only, false = mirror of server task
}
```

Server scheduler keeps owning user-visible cron (Pulses, reminders,
mail snooze — per `2026-05-20-automations.md`). Brain cron is the
device-side runtime that *executes* fires + runs its own housekeeping.
No competition, no duplication.

### `scheduler.Action.kind = "agent"` (new variant in `api/source`)

```json
{
  "kind": "agent",
  "operator": "trinity",
  "skill": "backend",
  "prompt": "check graph-1 disk usage and report"
}
```

When `loop.go` finds a due task with `kind: "agent"`, it publishes
`scheduler.claim_now` as today. The first device to claim runs brain
with the named operator + skill + prompt, posts the result back via
the existing devicebus `assistant.complete` envelope. The Flutter user
sees the result in their assistant timeline like any other run.

Trivial server change; the entire mechanism rides on the existing
devicebus + claim race + 60s expiry.

## Flutter changes

The Flutter app already speaks to source-api via devicebus
(`apps/construct/lib/src/assistant/client.dart`). Three additions for
1.2:

1. **Skill list view** — `lib/src/screens/skills/` — shows installed

   tools + their permission levels.
2. **Bundle picker on the assistant compose** — slash menu surfaces
   user + org bundles.
3. **Scheduled-agent timeline entries** — when a `scheduler.claim_now`
   fires and a device runs it, Flutter receives the completion via
   devicebus; entry shows "Scheduled by Trinity · Backend skill" with
   the original schedule visible.

No new transport. Everything rides the devicebus we already have.

## Marketplace changes

`api/marketplace` gains a Skills catalog parallel to Spaces:

- `GET /api/marketplace/skills` — public catalog with name, description,
  scope, trust tier, version, install count.
- `POST /internal/skills` — staff/developer publish, gated by gateway
  secret + developer enrollment (same path as Spaces).
- Trust tiers: `builtin` (ships with brain) · `official`
  (construct-space publisher) · `community` (developer-published, scanned).

Install flow:

```bash
construct skills install backend
# → resolves from marketplace
# → downloads tarball
# → verifies signature
# → unpacks to ~/.construct/profiles/<id>/skills/user/backend/
# → registers in local SkillRegistry
```

`construct skills tap add <gh-org>/<repo>` adds a custom registry
(community repo of SKILL.md dirs). Per
`feedback_brain_pi_shape`: skills discovered via `list_skills` /
`load_skill` — no surface inflation on the model side.

Web UI at `web/my` Marketplace tab adds a Skills section.

## Migration plan

Phase 1 — **brain refactor** (no user-visible change):
- Implement `SkillEntry.Tools` + sidecar runtime.
- Add `skill_manage` + `unload_skill` + tier-2 disclosure.
- Ship reference skills `graph`, `git`, `documents`, `org`, `marketplace`,
  `spaces` bundled with brain.
- Remove the hidden builtins they replace.
- Validation: existing operator behaviour unchanged on all our test
  prompts. Tool-call count per turn doesn't regress.

Phase 2 — **skill_manage live**:
- Telemetry counter for skills authored per session.
- Frontend Skills panel surfaces user-authored skills with review +
  edit + delete affordances.
- Bundles UI in compose.

Phase 3 — **marketplace + cli**:
- Skills section on marketplace-api.
- `construct skills install / tap / publish` in CLI.
- Web UI Skills section.

Phase 4 — **trajectory pipeline**:
- ShareGPT export with consent toggle.
- telemetry-api ingest + storage.
- Daily roll-up to per-operator JSONL.
- First fine-tune: Trinity LoRA on Trinity traces via mlx-lm-lora DPO,
  per `provider_mlx_lm_dpo.md`. Validate offline before rotating into
  production.

Phase 5 — **scheduler.agent**:
- `scheduler.Action.kind = "agent"` server-side.
- `brain/cron` `ServerFireJob` receiver.
- Flutter scheduled-agent entries.

Phases 1–3 are 1.2.0. Phases 4–5 are 1.2.1 / 1.2.2 — separated because
trajectory consent + fine-tuning is a privacy / billing conversation,
and scheduler-agent needs Phase 3 done first so the listed `skill` in
the action resolves to something installable.

## What's explicitly out of scope for 1.2

- **Docker / SSH / Modal sandbox backends.** Spaces sandbox + bash
  covers actual workloads.
- **Kanban swarm.** Operator family + devicebus already does
  multi-agent at the right layer.
- **ACP adapter.** Partner-driven; revisit when a concrete partner asks.
- **MCP server mode for brain.** Defer to 1.3 — it's a real surface
  worth shipping, but it needs its own design pass (which 10 tools to
  expose, how session ownership works when Cursor drives brain).
- **Vector-store memory.** Auto-memory + procedural skills cover the
  observed cases. Add only if a real gap shows up.
- **Re-importing old operator's `morpheus` / `verification` /
  `coreagents` / `swarm` packages.** Bring across ideas, not code; the
  brain rewrite was deliberate.

## Open questions

1. **Auto-unload timing.** Unload at end_turn? At session end? After N
   idle minutes? Default proposal: session end. Configurable per skill
   via `unload: end_turn | session | manual`.
2. **Tool permission UX for `prompt` permission.** Same modal as
   today's `ask` permission gate? Or a one-time "Allow this skill's
   tools for this space" with revocation in settings? Lean toward the
   latter — fewer prompts, scoped trust.
3. **Skill versioning + lock.** When marketplace publishes `backend
   0.4.0`, do user-modified local copies auto-update or stay pinned?
   Hermes uses a `.bundled_manifest` hash; we should do the same.
4. **Signing.** Skills carry sidecar binaries; binaries should be
   signed by the publisher and verified by brain on install. Use the
   existing space tool signing flow from `2026-05-04-space-binary-sandbox.md`?
5. **First operator to dogfood `skill_manage`.** Trinity (text + tool
   dispatch) is the obvious candidate. Tank (code) second — both
   produce trajectories rich enough to be worth synthesising.

## Success criteria

- **Tool-surface size:** visible per-turn schema drops below 8 tools;
  hidden builtin count drops below 10 (from ~25).
- **Skill authoring:** at least one user-authored skill survives a
  session reset and re-loads correctly the next time.
- **Trajectory volume:** ≥ 100 consent-flagged traces/day flowing to
  telemetry-api within two weeks of Phase 4.
- **Scheduler-agent:** a Pulse-style "every morning at 9, run Trinity
  with the `oracle-health` skill" job fires correctly on whichever
  device is online.
- **Operator regression:** zero observed regression in existing
  operator behaviour vs 1.1.x on the live test prompts.
